# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Система поддерживает функцию управления отоплением в доме путем прямого обращения к ней.
- Пользователи могут удаленно управлять отоплением в доме (включать/выключать) через веб-интерфейс.
- Система обеспеивает возможность регистрации устройств (подключение системы отопления к системе управления обеспечивается силами выездного инженера, что говорит о том, что текущая версия может даже содержить, например, какой-то административный интерфейс - по условию не ясно).

**Мониторинг температуры:**

- Система поддерживает функцию получения данных о температуре с датчиков, установленных в домах, путем прямого обращения к ним.
- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс.

### 2. Анализ архитектуры монолитного приложения

- Архитектура приложения: монолит
- Язык программирования: Go
- База данных: PostgreSQL
- Взаимодействия: исключительно синхронные
- Способ развертывания: неизвестен (но для пущего ужаса можно предположить, что напрямую на сервере запускается нативный бинарный исполняемый файл)
- Масштабирование: возможно вертикальное масштабирование и горизонтальное - за счет увеличения реплик и настройки балансировщика. Однако нет возмности масштабировать отдельно взятые части приложения.

### **4. Проблемы монолитного решения**

Проблемы текущего решения проистекают от целей, которые перед собой ставит компания. Их можно разделить на 2 категории: функциональные и архитектурные/инфраструктурные.
Поэтому если идти от задачи разделения текущего приложения на микросервисы, можно выделить следующие функциональные проблемы:
- отсутствие возможности самостоятельной регистрации устройств в системе
- отсутствие возможности регистрации новых типов устройств
- отсутствие возможности автоматизации сценариев

Здесь, как следствие, прослеживается и потенциальна экономическая проблема: высокие затраты на ФОТ и накладные расходы в части выездных инженеров, которые занимаются подключением. Также пользователи в процессе подключения системы зависимы от инженеров, что ограничивает их в контексте гибкости.

А также можно проследить следующие архитектурные и инфраструктурные проблемы:
- невозможно масштабировать отдельные части приложения (например, сервис сбора данных с датчиков)
- риск проблем при развертывании - нет гарантий, что команда разработки использует то же окружение, что и на продуктивном контуре
- ничего не известно про наличие или отсутствие инструментов непрерывной сборки и непрерывного развертывания (непрерывной доставки)
- отсутствие декомпозции как риск-фактор для работы команды в 5 разработчиков
- отказ приложения = отказ всей системы
- работоспособность и скорость синхронных взаимодействия в какой-то момент может упереться в физические ресурсы сервера 

С другой же стороны, в целевой картине компания планирует создание приложения по модели SaaS (по умолчанию не противоречит тому, что реализация может быть монолитной), основная функциональность - управление умными устройствами и сбор телеметрии, в то время, как подключение и настройка сценариев - второстепенные функции с гораздо меньшим профилем нагрузки. В таком контексте допустим вывод, что система может работать, будучи монолитом и может быть масштабирована горизонтально целиком. При этом что можно было бы улучшить:
- реализовать целевую функциональность по модели SaaS
- упаковать приложение в docker-образ и развертывание осуществлять с помощью контейнеров
- в ландшафт внести балансировщик нагрузки для возможности масштабирования
- кластеризовать БД (например, репликация по приципу master-slave), тем самым реализовать отказоустойчивую конфигурацию
- реализовать асинхронные взаимодействия для упрваления нагрузкой и повышения отклика в части работы пользователя с web-интерфейсом

# Задание 4. Создание и документирование API

### 1. Тип API

Микросервисы имеют REST API, с помощью которого API Gateway маршрутизирует пользовательские запросы с web и мобильного приложений.

Межсервисное взаимодействие предлагается реализовать в асинхронном подходе. Почему:
1. Подавляющее большинство пользовательских запросов в системе будет в части управления умными устройствами;
2. Умные устройства, находясь во внешнем по отношению к разрабатываемому ПО контуре, имеют свои риски в части бесперебойной работы: слабый интернет канал, отсутствующее питание, прочие неполадки;
3. Таким образом в случае наступления ошибочной ситуации клиентское приложение будет ожидать синхронное выполнение запроса, блокируя работу пользователя с интерфейсом.

Выходом из данной ситуации служит подход, при котором пользовательская операция фиксируется и продуцирует событие, которое "подписчики" позднее обрабатывают и реализуют необходимое поведение.

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql
